# [Beneficios y promociones] - Topes por usuario y por período - Feature Flag de encendido/apagado / Toast de aviso llegaste al Límite

## Description

**Como** Team Analyst de Billetera Bezza
**Quiero** implementar un mecanismo de Feature Flag para el control de topes de reintegro por usuario y rubro (MCC) en la arquitectura BFF, retornando en la API el estado de límite alcanzado y los textos del mensaje informativo
**Para** realizar un rollout progresivo y seguro, mitigar riesgos de doble acreditación, asegurar la precisión monetaria sin desvíos y notificar dinámicamente al usuario en el comprobante únicamente cuando consuma la totalidad de su beneficio mensual.

### Objetivo

Estabilizar el flujo de cashback e implementar el control de topes mensuales por usuario y por categoría (MCC) operando bajo lógica transaccional atómica e idempotente. La solución se habilita mediante una Feature Flag que, al estar encendida y detectar que la transacción agota el saldo tope del periodo, retorna en el BFF el atributo `show_limit_reached_message = true` junto con los campos de texto (`limit_reached_message_title` y `limit_reached_message_body`) para que la App Mobile despliegue el banner informativo en Pantalla de Resultado Exitoso.

### Descripción General

Actualmente, el sistema legacy presenta vulnerabilidades de sincronización entre el procesamiento en tiempo real (BFF) y los procesos diferidos (Jobs Batch), exponiendo a la billetera a duplicación de reintegros y pérdidas de precisión por el uso de flotantes.
Esta iniciativa aborda el endurecimiento del flujo (Hardening) con el uso estricto de `BigDecimal` (escala 2) y el control atómico sobre las tablas de configuración, consumo y deduplicación (`cashback_mcc_tope_config`, `cashback_entitlement_usage_mcc`, `cashback_entitlement_tx_dedup`), integrando un Feature Flag de encendido/apagado.

## Acceptance Criteria

### 1: Pago QR con Feature Flag encendida que agota el tope mensual de reintegro

**Dado** que el sistema tiene la Feature Flag de topes encendida
**Y** el monto de reintegro de la compra alcanza o agota el disponible mensual para el rubro/MCC
**Cuando** realiza un Pago con QR
**Entonces** el BFF procesa el cálculo atómico en BigDecimal y actualiza las tablas de consumo y deduplicación por tx_id
**Y** devuelve en la respuesta de la API el atributo `show_limit_reached_message` en True
**Y** devuelve en la respuesta el título `limit_reached_message_title` igual a "¡Le sacaste provecho a Bezza!"
**Y** devuelve en la respuesta el cuerpo `limit_reached_message_body` igual a "Llegaste al límite de reintegros de este rubro. Se renuevan el 1 del mes que viene."
**Y** la App muestra en la Pantalla de Resultado Exitoso de pago el Toast informativo azul con el título y mensaje devueltos por la API

### 2: Pago QR con Feature Flag encendida que NO agota el tope disponible

**Dado** que el sistema tiene la Feature Flag de topes encendida
**Y** la compra genera un reintegro que mantiene un disponible restante mayor a cero
**Cuando** realiza un Pago con QR
**Entonces** el BFF actualiza de forma atómica el consumo acumulado en las tablas de topes
**Y** devuelve el atributo `show_limit_reached_message` en falso
**Y** no envía los textos del mensaje de límite alcanzado
**Y** la App muestra la confirmación del pago con el beneficio otorgado sin desplegar el banner informativo

### 3: Pago QR con Feature Flag encendida cuando el usuario ya no tiene disponible

**Dado** que el usuario tiene la Feature Flag de topes encendida
**Y** el disponible de reintegro para el MCC es igual a cero antes de la transacción
**Cuando** realiza un Pago con QR
**Entonces** el BFF registra la denegación por tope y deriva la transacción al flujo de pago tradicional
