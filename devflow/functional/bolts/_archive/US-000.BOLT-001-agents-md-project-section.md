# US-000.BOLT-001 — A methodology upgrade never destroys the project's own section of AGENTS.md

---

## 1. Description

The distributable must guarantee that a methodology upgrade replaces the
framework part of a project's root `AGENTS.md` while preserving, byte for
byte, the part the project itself authored.

---

## 2. Expected outcome and completion evidence

- **Objective:** close the defect by which Avenga DevFlow invites a project to
  extend its root `AGENTS.md` and then, at upgrade time, provides no rule that
  protects what the project wrote there — so that content is lost silently, in
  every adopting project, on every upgrade.
- **Completion criterion:** after an upgrade performed as the methodology
  prescribes, the project-authored part of `AGENTS.md` is unchanged and the
  framework part is the new version's. The boundary between the two is stated
  normatively and is identifiable by an agent executing the migration without
  human judgement.
- **Expected evidence:**
  1. A simulated upgrade of this repository: `git diff AGENTS.md` shows changes
     only in the framework part; nothing below the boundary differs.
  2. The four platform agent definitions remain byte-identical in their shared
     methodology body — the sanctioned `agents-data/` path being the only
     divergence — and every blocking rule is still present in all four.
  3. No agent definition still directs project-authored content into a file the
     upgrade overwrites wholesale.
  4. A repository-wide search shows no remaining statement contradicting the
     new rule.
- **Scope:**
  - the normative migration procedure and the structural text it depends on;
  - the blocking-rule projection that makes the loss a violation rather than an
    accident;
  - the `AGENTS.md` the distribution ships, including where its boundary sits;
  - the four platform agent definitions, changed as one synchronized edit;
  - this repository's own root `AGENTS.md`, brought into the shape the rule
    assumes.
- **Exclusions:**
  - running the actual release migration of this repository — a later, separate
    outcome;
  - any version bump;
  - the changelog's removal from the distributable, already delivered;
  - tooling that could check the invariant automatically (`tools/`).
- **Risks / controls:**
  - *A change to shared agent content lands in fewer than four files.* Control:
    the four-way body diff is part of the expected evidence, not an optional
    check.
  - *The boundary is placed so that framework text ends up on the project side,
    freezing it in every adopting project.* Control: evidence item 1 must show
    the framework part actually updating.
  - *Rule 6 of ADR-001 stays unenforced.* Control: evidence item 3 plus the
    blocking-rule projection named in scope.

## 5. Does this Bolt need splitting?

No. The outcome holds only if every part of it lands together: a normative
rule with no boundary in the shipped file is unenforceable, a boundary with no
rule is decoration, and agent definitions contradicting either one reintroduce
the defect. There is exactly one demo criterion and no part is independently
acceptable.

Estimated with the AI-native rule (§2.4): one V-Bounce × (agent generation +
the review budget for the assigned risk class) + SPEC review + acceptance +
the four-way verification — inside the 1h–1 working day target, well below the
splitting threshold.
