## 1. Description

The **per-project AITL-enable ADR template** (DISC-001 §5.6.3, DISC-002
rec #7) ships in the kit's `actors/` folder: the one governed act that
enables virtual approvers — declaring the enabled checkpoint classes, the
roster contents, and the instantiated approver charters (never a silent
flag). Plus the **resolution-rule text**: role → actors (humans and agents
as peers; agent holders count only for enabled checkpoints), the
production lookup (who produces — resolved from `role`), the independence
floor/hardening/ceiling ladder (ADR-008 §3.3), and the zero-config
invariant (no roster / no `agents:` → pure HITL).

---

## 2. Expected outcome and completion evidence

- **Objective:** the governing act that makes delegation explicit + the
  rules that make the roster a deterministic lookup.
- **Completion criterion:** the AITL-enable ADR template exists in
  `actors/` (fields: enabled checkpoints, roster contents, approver
  charters, human-only floor); the resolution-rule text is stated
  (role → actors, production from role, independence ladder, zero-config).
- **Expected evidence:** the template diff + the resolution-rule text
  presence; consistency with ADR-008 (§3.2/§3.3) and the roster schema
  (BOLT-001).
- **Scope:** the kit's `actors/` folder (the template) + the
  resolution-rule text (roster docs / methodology).
- **Exclusions:** the schema itself (BOLT-001); the US-001 absorption
  (BOLT-003); the root `devflow/` (ADR-004).
- **Risks / controls:** the template enabling delegation silently —
  controlled by the one-act rule (the ADR is the only door) and the
  human-only floor (ADR-008).

---

## 3. Covered acceptance criteria

> Reference the ACs of the parent artifact — never write new ones here
> (§2.4, §2.6).

- `AC-2` (US-024) — **Given** the zero-config invariant, **When** no roster
  (or no `agents:` section) is present, **Then** the project behaves
  byte-for-byte as pure HITL — stated in the resolution-rule text.
- `AC-3` (US-024) — **Given** a lookup for who produces an artifact class,
  **When** the team needs an executor, **Then** the roster returns the
  actors holding the role that owns it (production mapping resolves from
  `role`) — stated in the resolution-rule text.
- `AC-4` (US-024) — **Given** a checkpoint's recommended role, **When** an
  approver must be resolved, **Then** the roster returns the actors holding
  that role (peers; agent holders only for enabled checkpoints).
- `AC-5` (US-024) — **Given** the independence floor, **When** an approval
  is routed, **Then** `approver.id ≠ executor.id`, model hardening at
  `high`, human-only at `critical`/`regulatory`; a violating routing is
  refused by the Coordinator. **Two actors sharing one `definition`** stay
  independent at the actor level (distinct `id`) — one may approve the
  other's work at low/medium; at `high`, model hardening requires them to
  carry distinct per-instance `model`s (the roster's per-actor `model`
  makes this possible).
- `AC-7` (US-024) — **Given** the per-project AITL-enable ADR template,
  **When** a project enables virtual approvers, **Then** one governed act
  declares the enabled checkpoints, the roster contents and the
  instantiated approver charters — the template ships in `actors/`;
  enabling is never a silent flag.
