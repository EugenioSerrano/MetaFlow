---

## 1. Description

Document, in the §5.16 Methodology Upgrade Protocol, how manifests convert from
`schema_version "4.0"` to `"5.0"` when a project (or the root) upgrades to v5.0 —
extending the existing `3.0`→`4.0` example — under the G36 no-history-rewrite
rule.

---

## 2. Expected outcome and completion evidence

- **Objective:** a project running §5.16 to reach v5.0 has a clear, correct
  manifest-conversion recipe.
- **Completion criterion:**
  - §5.16 documents the `4.0`→`5.0` conversion: each `hitl_approvals[]` entry
    becomes a `checkpoint_approvals[]` entry with `mode: human`; the historical
    `HITL-*` checkpoint name is **preserved** (never rewritten, G36); no recorded
    value invented or dropped; `schema_version` set to `"5.0"`.
  - A worked before/after example (a v4.0 manifest → its v5.0 form) is shown and
    the v5.0 form validates against the v5 schema (BOLT-001).
- **Expected evidence:** the §5.16 text carries the `4.0`→`5.0` conversion; the
  worked example validates green; `git status` shows only `distribution-kit/`.
- **Scope:** the manifest-conversion part of §5.16 + the worked example.
- **Exclusions:** other v5.0 migration concerns (how the HITL→AITL rename or the
  `agents/` registry migrate → their own USs); converting this repo's actual
  manifests (that runs when the root migrates to v5.0 — a future §5.16 event).
- **Risks / controls:** conversion that rewrites history — control: the AC
  mandates historical `HITL-*` names preserved (G36); example drift from the
  schema — control: the worked example validates against BOLT-001's v5 schema.
