# US-000.BOLT-014 — §5.16: input/ scaffolding vs raw evidence clarification (BUG-004)

| Field        | Value |

| **Type**     | non-functional |

| **service_class** | feature_value |
| **Demo / completion evidence** | The §5.16 migration rules explicitly distinguish input/ framework scaffolding (replaced by the new version; preserved only when the project modified it) from raw evidence (copied byte-for-byte, G31), the post-migration verification catches byte-level differences of evidence, and the statement is identical in the operating methodology and the distribution-kit copy (parity) — with zero change to any other rule (G-count 39, agents untouched) |

---

## 1. Description

Clarify the §5.16 migration procedure (in `devflow/avenga-devflow/Avenga-DevFlow.md`
and its distribution-kit copy, in parity) so the two colliding normative rules
evidenced by BUG-004 no longer conflict: the `input/`-in-full byte-for-byte rule
and the README/INDEX-never-copied-forward rule. The clarified text states that
the framework scaffolding shipped inside `input/` (the kit's own README/INDEX
files) is replaced by the new version, unless the project modified such a file
— in which case it is evidence and is preserved byte-for-byte — while every
other file inside `input/` is raw evidence, copied byte-for-byte and never
overwritten (G31). The post-migration verification is strengthened so it
detects byte-level differences of evidence (it can no longer pass while
evidence bytes differ). This is a localization/clarification of one section;
no other methodology rule, guardrail, agent definition, schema or tooling
changes.

---

## 2. Expected outcome and completion evidence

- **Objective:** §5.16 contains an unambiguous precedence rule for `input/`
  files (scaffolding vs evidence) and a verification that cannot miss a
  byte-level difference of evidence, stated identically in the operating
  methodology and the distribution-kit copy.
- **Completion criterion:** the reproduction of BUG-004 no longer holds —
  the prescribed verification is defined in terms that would fail on a
  byte-differing evidence file, and the scaffolding carve-out is explicit.
- **Expected evidence:** RED (before the fix, this V-Bounce): the §5.16
  prescribed check (tree + file count) passes while all 9 scaffolding files
  differ at the byte level (11 lines), with the commands and their output
  recorded. GREEN (after the fix): the same reproduction plus a positive-coverage
  sweep (ADR-005) shows the carve-out and the strengthened verification present
  in both trees, a parity diff of the two methodology copies shows no drift in
  the §5.16 region, and a scoped diff shows zero changes outside the §5.16
  text of the two methodology files (G-count 39×5 and the four agent
  definitions untouched).
- **Scope:** the §5.16 text of `devflow/avenga-devflow/Avenga-DevFlow.md` and
  `distribution-kit/devflow/avenga-devflow/Avenga-DevFlow.md` (parity), plus
  any sentence in the same two files that states the `input/` copy rule and
  must be aligned with it (phrase-family, ADR-005).
- **Exclusions:** no changes to G31 or any other guardrail; no changes to the
  other §5.16 steps (AGENTS.md merge, LANGUAGE/VERSION, CHANGELOG, routing,
  manifests); no changes to agent definitions, schemas, `bin/` tooling, or
  any other section of the methodology; this migration's already-accepted
  resolution (new scaffolding in `input/`) is not reverted.
- **Risks / controls:** risk of partial sweep (stale phrasing elsewhere in the
  same files) → controlled by the ADR-005 phrase-family positive-coverage
  sweep; risk of kit/root drift → controlled by the parity check in the
  completion evidence.
